# Introduction

When I was a kid in the early 2000s, I spent a lot of time playing games that I borrowed from our local library. Many of them were German Point-and-Click adventure games since those were the games that ran on my dad's Windows 95 computer. Even back then I was interested in tech always tried to figure out a way how I could keep playing these games after giving them back to the library but I, of course, never managed to do it. 
A few days ago, I stumbled over one of those failed attempts again: a set of CDs that I tried to burn a copy of "Findus bei den Muklas" on and figured that maybe now is the time that I could finally do it.

# Getting a disk image

Obviously, the CD I burned back then was unusable. Both because the CD burners at the time often weren't really able to properly read or write CDs with copy protection on them but also because I haven't had a computer with a disk drive in the past 10 years.

<Figure src={import("assets/limited_by_the_technology_of_my_time.png")} alt="disappointment.png"/>

Thankfully some helpful soul uploaded a set of full disk images for that and all the other games of that series to :link[archive.org]{id="https://archive.org/details/cd-01_202304"}). It's not piracy if it's on there, right?

## Unpacking the Image

The Game came as a set of 3 files, a `.ccd`, a `.cue` and a `.img` file. Those are apparently produced by the old :link[CloneCD Program]{id="https://en.wikipedia.org/wiki/CloneCD"} and contain the raw data from the disk plus additional out-of-band information such as track information. Games from that time often came with Audio tracks on them as well so you could just pop these CDs into a CD player and listen to the soundtrack or other bundled media.

Looking at the `.cue` file shows that there's a <TechnicalTerm client:load term="MODE1 track">These are Tracks meant for storing regular data such as a file system. They are usually skipped by Audio players</TechnicalTerm> at the start containing the game files and then seemingly 3 `AUDIO` tracks after that:

```cue title="CD01.cue"
FILE "CD01.img" BINARY
   TRACK 1 MODE1/2352
   INDEX 1 00:00:00
   TRACK 2 AUDIO
   INDEX 1 45:08:37
   TRACK 3 AUDIO
   INDEX 1 46:38:44
   TRACK 4 AUDIO
   INDEX 1 47:08:50
   TRACK 5 AUDIO
   INDEX 1 47:11:58
```

To be able to access the data, I just used the old `ccd2iso` tool which failed when it hit the first `AUDIO` track but was still able to convert the start of the file into a regular ISO that can be mounted.

# Copy Protection 1

Mounting the file and trying to copy the data over, I ran into what I believe to be the first copy protection measure:

<Figure src={import("assets/duplicate_files.png")} alt="Duplicate files popup while extracting the archive"/>

Some of the files seem to be in the disk image multiple times. Once as the real copy and once as a second copy that was either 0 bytes or 256 bytes long and contained random garbage. 
My guess is that they did that on purpose to trick some tools to only display the fake decoy copy of the file instead of the real one. Since most older media like magnetic tape or CDs couldn't really be rewritten, the data format they use has the ability to overwrite earlier records with new data that comes later on by just appending to the data. `.tar` archives also still work that way!

Using a combination of `PeaZip`, `Ark`, `Dolphin` and `7z`, I ultimately managed to extract the right files from the iso but it was mostly manual labour of choosing the files that were the right size and skipping the decoy ones.

<Figure src={import("assets/extracted_files.png")} alt="Final files that were extracted from the iso image"/>

At this point, just running the installer felt the easiest and surprisingly just worked. I ran it using `WINEPREFIX=$(pwd)/prefix wine "Installiere Findus4.exe"` to make it install into a separate WINE prefix from which I could just copy the installed data out of afterwards.

# Copy Protection 2 - Elecric Boogaloo

Executing the `Findus4.exe` now of course didn't just work but instead showed a nice error popup that I'm missing the CD.

<Figure src={import("assets/missing_cd.png")} alt="Missing CD Error popup"/>

Simply `grep`ping for that message using `rg -a "Lege die CD"` showed that they just read that message from the `Pettson3.ini` file. _They apparently didn't even bother renaming that file from the previous game._

```ini title="Pettson3.ini"
[CDROM]
CDROM=?
[GAME1]
Vind=0
[ALERT1]
MESSG=Lege die CD Findus4 ein und versuche es noch einmal.
[SCREEN]
FULLSCREEN=1
```

`grep`ping for a few strings ultimately led to `messg` being found in `Findus4.exe`. First instinct was of course to just throw the binary into Ghidra and start looking for it. Surprisingly, the string didn't show up anywhere there using the `Search -> For Strings...` option which usually means that the string isn't actually part of the PE data but some sort of extra payload that was appended to the end of the executable file.

## Extracting the embedded script

After some more digging I found that these games are all `Macromedia Director Projector` executables. These are executables that were generated by Macromedia Director and basically contain the whole runtime for interpreting director files and have a .dxr file `cat`ted onto the end of the file which is what gets executed when the program runs. It made sense that the CD check would be part of that embedded director file because why would the runtime read from a config file called `Pettson3.ini`.

During my research, I stumbled over :link[ProjectorRays]{#ProjectorRays/ProjectorRays} which is a disassembler and decompiler for exactly these files. They have the file signature `RIFX` or `XFIR`, depending on the endianness of the target system, which makes them pretty easy to identify. Using ImHex, I found a few occurrences of those strings in the binary. From the source code of ProjectorRays, the format of these dxr files starts with something like this:

```pl title="director.hexpat"
enum Codec : u32 {
    MV93 = le u32("MV93"),
    MV95 = le u32("MV95"),
    FGDM = le u32("FGDM"),
    FGDC = le u32("FGDC"),
    APPL = le u32("APPL")
};

struct Content {
    type::Size<u32> length;
    Codec codec;

    // ...
};

struct DirectorFile {
    char magic[4];
    if (magic == "RIFX")
        be Content content [[inline]];
    else if (magic == "XFIR")
        le Content content [[inline]];
    else
        std::error("Invalid Director File!");
};
```

Only two of `XFIR` occurrences had a valid Codec after them: One being `APPL` at address `0x00222151` which looks like a Apple Macintosh-specific script, and one being `MV93` at address `0x002222F0` which seems to be the common script. 

I initially tried to copy out that chunk from the executable and process it separately using ProjectorRays but it turned out that all the offsets used inside of the appended file are absolute so they were adjusted to work with the dxr file not starting at the beginning at the file. Instead, I ended up hacking in a `--offset` option into the CLI that lets you seek forward to the actual offset of the embedded binary. (PR can be found here in case it's useful to somebody else: :link[ProjectorRays#63]{id="https://github.com/ProjectorRays/ProjectorRays/pull/63"}).

## Disassembling the Director File

Finally, after all this trouble using the following command we can dump the embedded director file's content. 

```sh frame="terminal"
./projectorrays decompile Findus4.exe -o output --dump-scripts --offset 0x002222F0

output
├── Findus4
│   └── casts
│       └── Internal
│           ├── MovieScript 1.lasm
│           └── MovieScript 1.ls
└── Findus4.dir
```

To my surprise, this generated both a disassembly file (the .lasm file) **and** a decompiled version of the script (the .ls file) which still contains all the original function and variable names! 

<Figure src={import("assets/decompiled_script.png")} alt="Decompiled Director Script"/>

## Analyzing the script

The generated file is only around 150 lines long and contains the init logic of the game. It's written in a programming language called :link[Lingo]{id="https://en.wikipedia.org/wiki/Lingo_(programming_language)"} which is what Macromedia Director uses. Even without knowing the language, it's pretty straight-forward to read. It didn't take long to find the function where that `"messg"` string originally came from. As seen here, they implemented a primitive `.ini` file parser here to parse the `Pettson3.ini` file and get a few config values out of it, one being the error message displayed when no CD can be found.

```Lingo title="MovieScript 1.lasm"
-- ...
on analyseIniText iniText
  repeat with mening = 1 to iniText.line.count
    ReddString = StripString(iniText.line[mening])
    if ReddString contains "[" then
      ReddString = StripString(iniText.line[mening + 1])
      antalBokstaver = ReddString.char.count
      if ReddString contains "cdrom" then
        cdromenhet = ReddString.char[7..antalBokstaver]
      end if
      if ReddString contains "Vind" then
        antalBokstaver = ReddString.char.count
        vindspelAktivt = integer(ReddString.char[6])
      end if
      if ReddString contains "messg" then
        antalBokstaver = ReddString.char.count
        alertmessage = ReddString.char[7..antalBokstaver]
      end if
      if ReddString contains "fullscreen" then
        antalBokstaver = ReddString.char.count
        fullscreen = integer(ReddString.char[12])
      end if
    end if
  end repeat
  resultat = [#cdromenhet: cdromenhet, #vindspelAktivt: vindspelAktivt, #alertmessage: alertmessage, #screen: fullscreen]
  return resultat
end
-- ...
```

</NotePanel>

A bit further down, we can also find the function where the error text is actually being used:

```Lingo title="MovieScript 1.ls"
on checkpccdrompath
  seperator = the last char in the applicationPath
  drivelista = ["d", "e", "f", "g", "h", "i", "j", "k", "l", "m", "n", "o", "p", "q", "r", "s", "t", "u", "v", "w", "x", "y", "z"]
  Retvar = VOID
  repeat with Drive in drivelista
    iscdrom = baDiskInfo(Drive, "type")
    if iscdrom = "CD-ROM" then
      Path = Drive & ":" & seperator & "p3media"
      if checkoncd(Path) then
        Retvar = Drive
        exit repeat
      end if
    end if
  end repeat
  return Retvar
end

-- ... Part of setSearchPaths function
driveletter = checkpccdrompath()
if not voidp(driveletter) then
  ini[#cdromenhet] = driveletter & ":"
  hdMedia = mp & "p3media"
  hdljud = mp & "p3media\p3ljud"
  hdcast = mp & "p3media\p3cast"
  cdMedia = string(ini.cdromenhet & "\p3media")
  cdLjud = string(ini.cdromenhet & "\p3media\p3ljud")
  cdCast = string(ini.cdromenhet & "\p3media\p3cast")
  the searchPaths = [hdMedia, hdljud, hdcast, cdMedia, cdLjud, cdCast]
else
  alert(string(ini.alertmessage))
  quit()
end if
-- ...
```

Again, pretty straight forward code. They just loop over all possible Windows Drives, trying to find one that contains a CD-ROM with the `p3media` folder on it. If that is found, the search paths are setup, otherwise the error message we saw is displayed and the game calls `quit()`.

## Patching the script

Analyzing the `setSearchPaths` function a bit, I figured the easiest way avoid the `quit()` branch being executed while still allowing it to setup the search paths correctly would be to patch the `if` there to just jump to the next instruction instead of to the `else` branch if the check failed. That would result in the CD paths being a bit weird but I figured it would probably still work since the game lets you do a "Full Install" where it copies all the required data to the hard disk and presumably also loads the files from there then.

In the assembly file, the instructions we want to patch are these here:
```sh frame="code" title="MovieScript 1.lasm"
< 95 00 60       > [246] jmpifz [342] ......... if not voidp(driveletter) then / else
< 4C 08          > [249] getlocal 8 ........... <ini>
```

ProjectorRays sadly doesn't yet support assembling the code back but thankfully, the Lingo bytecode is incredibly simple so we can do it manually with ImHex. Every instruction starts with a single opcode byte, followed by a big endian integer that's either 1, 2 or 4 bytes long. To make the manual patching a bit easier for me, I made ProjectorRays also output the bytes each of the instructions are made up of to the file (also PRd back to ProjectorRays).

Now for the patching, `jmpifz` has the opcode byte `0x95` followed by a big endian 16 bit relative offset `0x0060 / 96` of where to jump to. So to simply jump to the next instruction, we need to jump 3 bytes forward (from offset 246 to offset 249) so we want to patch the instruction bytes to be `< 95 00 03       >`. Searching for the original byte sequence yielded only a single result which I overwrote with the new instruction.

And with that, the game's intro video was playing! 🎉

# Copy Protection 3 - Rise of the Machines

Sadly, there was more to it.

<Figure src={import("assets/copy_protection.png")} alt="disappointment2.png"/>

Again, simply `grep`ping for that string yielded two results and I decided to start with `intro.dxr` for now

```sh frame="terminal" title="Grepping Error Message 2"
➜  rg -a 'Disc Error !'  

P3media/intro.dxr
...

P3media/huset.dxr
...
```

Throwing it into ProjectorRays again resulted in a few more scripts out of which one was pretty straight-forwardly called `BehaviorScript 36 - Call Copy-X CD protection DLL (OPTGRAPH.DLL).ls`. _I didn't need that much handholding, devs, but thanks either way._

Inside was, like the file name described, some code that loads the `optgraph.dll` that exists next to the game executable and calls the `initdisplay()` function inside of it. It then checks that the return value of that function and if it doesn't match some magic value, the game is once again aborted.

```Lingo title="BehaviorScript 36 - Call Copy-X CD protection DLL (OPTGRAPH.DLL).ls"
on exitFrame me
  if the platform contains "Mac" then
    nothing()
  else
    if Ok = 0 then
      alert("Disc Error !")
      avslutaSpelet()
    else
      if getReturnVal(me) <> 26079537 then
        alert("Disc Error !")
        avslutaSpelet()
      end if
    end if
  end if
end
```

Interesting to note here is, they didn't even bother implementing the copy protection for Mac...

To get past this check now, we have a few options. We could make the game believe that it's running on a Mac, we could patch the compare against the magic number or we could even just patch the dll to make it always return that constant. Seeing that the identical check is implemented again in `huset.dxr` and I didn't really want to RE the runtime and patch the platform detection, I decided to instead patch `optgraph.dll`.

## Patching the support dll

Opening the dll in Ghidra showed that it essentially only contained that one function and nothing else. 

`initdisplay()` itself is a bit of a convoluted mess where they send a bunch of low level commands to the CD Drive itself to somehow construct that magic value from it.

```c title="Ghidra Decompile - OPTGRAPH.DLL"
// ...
FUN_10001e50(&local_44,0,0x10);
local_3c = 3;
mciSendCommandA(local_c,0x814,0x100);
local_3c = 1;
local_2c = local_40;
mciSendCommandA(local_c,0x814,0x102,&local_44);
local_28 = (uint *)(local_40 & 0xff);
local_3c = 1;
local_48 = (char *)(local_40 >> 8 & 0xff);
local_38 = 4;
local_40._0_2_ = local_40._1_2_;
mciSendCommandA(local_c,0x814,0x112,&local_44);
// ...
```

I didn't spend too much time reversing any of this but instead just used Ghidra's wonderful `Patch Instruction` option to replace the first few instructions with a plain and boring `MOV` and `RET`.

```asm title="Ghidra Assembly Listing - OPTGRAPH.DLL"
**************************************************************
*                          FUNCTION                          *
**************************************************************
                        int __stdcall initdisplay(void)
                        assume FS_OFFSET = 0xffdff000
      int               EAX:4          <RETURN>
                      0x1060  1  initdisplay
                      initdisplay
10001060 b8 31 f1        MOV        EAX, 26079537
          8d 01
10001065 c3              RET
10001066 05              ??         05h
10001067 00              ??         00h
10001068 00              ??         00h
```

After struggling for an embarrassingly long time to get Ghidra to properly export the dll back out again, I finally managed to do it through `File -> Export -> Original File`.

This seemed to have been the last thing needed since the game is getting all the way to the menu screen now!

# Wrapping up

After spending the evening playing through that game again, I also looked through a few other, similar games that I used to play. Turns out a surprisingly big amount of them all used Macromedia and had essentially the exact same, basic copy protection mechanism. There's sadly no easy way to make a common patch that works for all of these games but with a little bit of effort, the exact same thing can be applied to these games as well.

Being able to still play these games again after over 20 years and maybe even having my future kid play them makes me really happy :) I hope this post will be able to bring the same joy to others as well!
